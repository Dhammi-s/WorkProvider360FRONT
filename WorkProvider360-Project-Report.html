1 Overview

WorkProvider360 is a multi-tenant SaaS: each customer (an “agency”) has its own isolated database, while a shared master database catalogs the agencies and their connection strings. Users sign in, are resolved to their tenant, and work inside role-based dashboards.

Roles

SuperAdminAdminManagerUser

IDs are static across tenants (1–4). Access is enforced both by JWT role claims and in the service layer.

2 Architecture

A classic N-tier / clean-ish layering on the backend, a component + service SPA on the frontend, and stored-procedure data access. Every server response is wrapped in a uniform envelope ApiResponse<T> = { success, message, data, errors }.

🖥️ Angular SPA (browser)
Standalone components + signals · Tailwind · route guards · HTTP interceptors (JWT + tenant header, error normalisation)
▼  HTTPS · JSON · Authorization: Bearer · X-Tenant-Domain
🌐 Controllers (ASP.NET Web API — WebApplication1)
Routing api/[controller] · [Authorize(Roles=…)] · claim helpers · ApiResponse<T>
▼
🧠 SaaS.BLL — Business Logic
Services (rules + role gating), security (hashing, JWT), payments (provider abstraction), email
▼
📦 SaaS.Core — Contracts
Entities · DTOs (Inbound/Outbound) · interfaces · constants · settings · exceptions
▼
🗄️ SaaS.DAL — Data Access (Dapper + Stored Procedures)
Repositories · TenantContext · TenantResolver · DbConnectionFactory
▼

Dependency direction: Controllers → BLL → Core ← DAL. Core holds the interfaces; BLL and DAL implement them; the Web project wires everything via DI.

5 Multi-tenancy model

Master database

Holds the Agencies table: AgencyId, AgencyName, DomainUrl, DbServer, DbName, DbUser, DbPassword, ConnectionString, IsActive, IsArchived, … — i.e. the catalog of tenants and how to reach each tenant DB.

Tenant database (per agency)

Holds all operational data: Users, Roles, Schedules, Applications, Offices, Invoices, POS, etc. One physical DB per agency, all created from the same SSDT template.

How the tenant is resolved (per request)

If the JWT carries an agency_id claim → resolve that agency by id (authenticated requests).
Otherwise (anonymous: login, apply, forgot-password) → use the X-Tenant-Domain header, else the request Host, matched against Agencies.DomainUrl.
The resolved agency's connection string is placed in the scoped ITenantContext; every repository then connects to that tenant DB.

The active demo tenant uses DomainUrl = localhost, so the frontend sends X-Tenant-Domain: localhost.

8 How a request works (end to end)

A component calls a core service (e.g. userService.getUsers()).
The auth interceptor attaches Authorization: Bearer <jwt> and X-Tenant-Domain.
The request reaches the API; JWT auth validates the token, then tenant resolution puts the agency's connection string in ITenantContext.
The controller (role-gated) calls a BLL service.
The service applies business rules / role scoping and calls a repository.
The repository (Dapper) executes a stored procedure on the tenant DB and maps rows to entities.
The controller wraps the result in ApiResponse<T>; the Angular service unwraps it into a signal; the UI renders.
Errors become AppException → clean status + message; the error interceptor surfaces it (and refreshes the token on a 401).

9 Feature modules

Authentication & roles

JWT login/refresh/logout, forgot/reset/change password, public user self-registration, one-time SuperAdmin bootstrap. Four roles with static IDs.

Hiring / role applications

Anonymous apply form (dynamic role dropdown + custom questions + expected salary), admin review with PDF export, approve → creates the user & emails credentials, reject → emails a notice. SuperAdmin settings control fields, questions, emails.

Offices & timezones

GUID offices with a per-office timezone (from a seeded reference list). Every Admin/Manager/User belongs to an office; SuperAdmin manages all, Admin only their own.

Scheduling & time

Schedules with pay rate + overtime, clock-in/out time entries, per-user pay reports, access levels (None/Read/Write), location pings / live map.

Announcements

SuperAdmin posts announcements; visible to Admin/Manager/User based on SuperAdmin visibility toggles (in Settings).

Email logs & branding

Every email is logged (Sent/Failed + body); SuperAdmin grants Admin/Manager log access. Agency logo uploaded + cropped in-browser, stored as base64, shown in the sidebar.

Invoicing / payroll

Admins/Managers paid their applied salary; Users paid computed shift wages. Cash or Stripe online. Browser-generated PDF (stamped PAID · CASH / ONLINE) emailed as an attachment; SuperAdmin accounting ledger of all invoices.

POS sandbox

Take a card sale via a pluggable IPaymentProvider (mock now, bank/Stripe later). A configurable platform fee (% + fixed) is the revenue; an earnings ledger + transactions prove the model — no real money.

11 Security

  • Auth: JWT Bearer, HMAC-SHA512 signed; claims carry agency_id, user_id, role_id, role name. Refresh tokens rotate; reset tokens are single-use with expiry.
  • Authorisation: declarative [Authorize(Roles=…)] on controllers/actions, plus service-layer checks for finer scoping (e.g. Admin → own office; log/announcement visibility).
  • Passwords: salted SHA-512 with constant-time comparison (documented as a deliberate, simpler-than-PBKDF2 choice).
  • Tenant isolation: each request is pinned to one tenant DB via ITenantContext; cross-tenant access isn't possible through the data layer.
  • CORS: configurable allowed origins; preflight handled before auth.
  • Payments: online payments are verified server-side against Stripe (PaymentStatus == "paid") before an invoice is recorded.

Hardening backlog: move committed secrets (DB password, JWT signing key, SMTP/Stripe keys) out of appsettings.json into environment variables; consider a stronger password hash (PBKDF2/Argon2); a “must change password on first login” step for emailed temp passwords.

12 Deployment

Database

Build the SSDT project → WorkProvider360.dacpac → publish to each tenant DB (post-deploy seeds reference data). Master DB holds the agency catalog.

Backend API

Publish the whole solution to runasp.net. Set secrets via env vars (Stripe__SecretKey, Smtp__Password, …). CORS + JWT configured in appsettings.

Frontend

Deployed on Vercel (root = client, output dist/client/browser, SPA rewrite to index.html). Prod build points apiBaseUrl at the API.
